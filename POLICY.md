# QuantumTrace 0.3 — assessment policy

Policy identifier: `junctionx-2026-context-policy-v2`. The challenge brief's
tiers describe primitives. They do not certify a protocol or implementation.
Version 0.3 adds the following explicit project rules; these extensions are
not attributed to the organisers or to NIST.

| Evidence | Project tier | Model / limit |
|---|---|---|
| Classical RSA, DSA, EC/ECDH/ECDSA, Ed25519/448, X25519/448 | critical | Shor exposure of the public-key component; a hybrid is assessed component by component |
| AES-128/192 | medium | Challenge symmetric-key policy, not a claim of a current practical break |
| AES-256, recognised final ML-KEM/ML-DSA/SLH-DSA family | resilient | Primitive family tier; exact parameters and implementation need separate verification |
| Deprecated MD5/SHA-1/DES/3DES/RC4 | medium | Challenge tier plus separate classical-security warning |
| Hash digest protecting a signature | medium/resilient | Ideal generic quantum collision-query exponent `n/3`; project target 128 |
| Known TLS-suite hash component | medium/resilient | Conservative collision model `n/3`; HKDF/MAC properties not independently established |
| Explicit preimage use / hash constructor inside detected PBKDF2 | medium/resilient | Ideal generic preimage-query exponent `n/2`; the password KDF remains separately unresolved |
| SHA-384/512 with unspecified purpose | resilient | Even the weaker generic collision model reaches the project target; implementation and construction not certified |
| SHA-256 with unspecified security purpose | unknown | Collision and preimage models give different tiers; context is required |
| Hash inside RSA-OAEP | unknown | Identified construction, but a dedicated construction-aware rule is not implemented; the RSA component still appears as critical |
| Exact `TLS_CHACHA20_POLY1305_SHA256` | resilient for ChaCha20 | IETF suite establishes a 256-bit encryption key; authentication, nonce use and key exchange remain separate |
| Bare ChaCha20 or AES without valid size | unknown | Exact variant/size required |
| HMAC-SHA-256 | unknown | Digest name does not prove key entropy, generation or actual tag length |
| PBKDF2-HMAC-SHA-256 | unknown | Output size/iterations do not prove password entropy; salt generation must be reviewed |
| Legacy Kyber/Dilithium/SPHINCS+ names | unknown | Exact version/variant required before final-standard claims |

`n/3` and `n/2` refer to idealised black-box **query complexities**, not seconds,
available hardware, practical attack budgets, or NIST security categories.
The quantum collision model entails resource tradeoffs. NIST guidance discusses
practical limits and different category definitions. The 128-bit target is a
project policy choice, not a prediction that a deployment is broken below it.
The SHA-256 TLS tier is deliberately conservative across hash roles.

Every finding exports an `assessment` object with its rule, scope, model,
target, query exponent (when relevant), and assumptions. Unresolved findings
also have `review_reason` and `missing_information`. The UI shows these in the
review queue and evidence dialog.

The score is the mean of critical 100, medium 50 and resilient 0, over rated
non-offered observations. Unknowns and offered TLS options are excluded and
displayed separately. Duplicate primitive observations affect the mean.
It is an exposure index, not a percentage probability or certification.
Comparisons warn when policies, supported input hashes or file coverage differ.

The source documents support the models/parameters; the tier mapping is the
project's policy extension. Technical explanations remain inspectable rather
than being generated by an LLM.


## Technical priorities (0.3.3)

`priorities` is a separate presentation aid, not another risk score. Source and
observed resource/session identify each group. Classical public-key inspection
considers negotiated, configured, public-key/certificate and static evidence in
that order; offers never create a migration action. Hybrid components stay
under construction review. Missing information and hash-policy checks have
explicit reasons and next steps. Every action references existing finding IDs.

The component risk weights are unchanged, including classical components inside
hybrids. The exposure index therefore continues to describe primitive tiers,
not the security of the combined hybrid. Deprecated algorithms also retain
separate classical-security concerns. No business impact is inferred.
